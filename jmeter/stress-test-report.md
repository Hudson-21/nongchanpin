## 二、项目与测试环境

### 2.1 项目简介

农产品溯源电商平台是一个面向农产品在线交易的 B2C 电商系统，解决农产品从展示、选购到交易、售后的一体化管理问题。系统采用 Struts2 + Spring + Hibernate + JSP 的 SSH 架构，前台面向消费者提供商品浏览与检索、商品详情、购物车、订单提交与支付、在线留言等功能；后台面向管理员与商家提供商品管理、商品分类管理、库存出入库管理、订单发货与退货处理、公告与轮播图维护、留言回复、会员管理以及销售/财务统计等功能。系统包含三类用户角色：游客、会员（买家）、管理员/商家。核心业务流程为：会员注册登录 → 浏览检索商品 → 加入购物车 → 提交订单 → 在线支付或货到付款 → 管理员发货 → 会员确认或申请退货 → 管理员处理退货并回补库存。本次压力测试即围绕上述核心流程中的高频接口与关键业务链路展开。

### 3.1 性能指标定义

| 指标 | 含义 | 本项目关注点 |
| --- | --- | --- |
| 平均响应时间 | 所有样本响应耗时的算术平均值 | 反映整体处理速度，用户直观感受 |

| P99 响应时间 | 99% 样本的响应时间不超过该值 | 反映长尾请求的劣化程度 |

| 错误率 | 失败样本数 / 总样本数 | 反映高负载下的稳定性与可用性 |

## 四、JMeter 测试计划设计

### 4.1 Test Plan 结构

每个场景对应一个独立的测试计划文件，结构一致，包含以下组件：

- **Test Plan**：测试计划根节点，禁用 functional_mode（不记录响应数据，减少开销）；
- **Thread Group（线程组）**：设置线程数、Ramp-Up、循环次数或调度器持续时间；
- **HTTP Request Defaults**：统一配置服务器 127.0.0.1、端口 8085、协议 http、编码 UTF-8；
- **HTTP Cookie Manager**：自动维护 JSESSIONID，保证会话类接口（登录、购物车）可用；
- **HTTP Header Manager**：设置 User-Agent 标识；
- **HTTP Request（7 个采样器）**：即第三章的 7 个接口，按顺序执行；
- **Summary Report（监听器）**：结果写入 .jtl 文件，供后续统计与生成 HTML 报告。

### 6.2 结果分析

1. **响应时间随并发显著上升**：并发从 20 增至 200（10 倍），平均响应时间增长约 6.9 倍，P99 增长约 8.4 倍，说明系统在高并发下产生明显排队，服务能力接近上限。
2. **吞吐量增长趋缓**：并发提升 10 倍而吞吐仅从 1386/s 增至 2013/s，说明服务器每秒处理能力存在天花板，新增并发主要转化为排队等待而非有效产出。
3. **错误率保持为 0**：在 200 并发以内系统仍能成功处理全部请求，未出现连接拒绝或请求失败，短期内可用性良好。
4. **页面类接口性能优异且稳定**：首页、商品列表、详情、搜索、公告、留言六个接口在全部场景下平均响应时间稳定在 2.1～3.3 ms，几乎不受并发影响，说明 JSP 页面渲染与简单查询不是瓶颈。
5. **登录接口是唯一显著瓶颈**：该接口响应时间从 80.5 ms（20 并发）劣化到 654.2 ms（200 并发），P95 达 1286 ms，是页面类接口的 200 余倍，也是拉高整体平均响应时间与 P95/P99 的主要因素。
6. **持续压力下的表现**：S6（50 并发持续 120 秒，共 181,261 个样本）平均响应 31.7 ms、P95 257 ms，与同并发的 S2（平均 34.6 ms）基本持平，说明 2 分钟持续负载下未出现明显的性能衰减或内存泄漏迹象。

## 七、性能瓶颈与问题分析

1. **登录链路开销大（首要瓶颈）**：memberLogin.action 每次请求都要经 Struts2 拦截器链、由 Spring 创建 Action 实例并注入 DAO、计算 MD5 摘要、执行 HQL 查询并创建 Hibernate Session，且未做任何缓存；相比直接访问 DAO 的 JSP 页面（2～3 ms），其开销高出两个数量级。并发 200 时 P95 达 1286 ms。
2. **数据库连接池未调优**：项目 lib 中同时存在 commons-dbcp、c3p0、proxool 三套连接池实现且均沿用默认配置，未针对并发设置最大连接数与初始连接数，高并发下连接获取成为串行瓶颈，这是登录等数据库密集接口响应时间随并发快速上升的直接原因。
3. **页面缺少缓存机制**：首页每次请求都要查询商品、公告、轮播图等多张表；项目已引入 ehcache 但未实际使用，导致大量重复的相同查询打到数据库。
4. **Tomcat 与 JVM 参数均为默认值**：未配置 maxThreads、acceptCount 等连接器参数，也未设置 JVM 堆大小（-Xms/-Xmx），高并发下线程调度与 GC 开销不可控。
5. **高负载下的稳定性风险（测试中发现）**：在 200 并发场景及 120 秒持续压力场景结束后，Tomcat 进程曾两次自行退出（后续请求报 Connection refused，Java 进程消失，未生成 hs_err 快照），说明长时间高负载运行存在进程崩溃风险，需结合 JVM 内存配置与日志进一步排查。
6. **健壮性问题**：会话缺失时，购物车等页面不是跳转登录页而是直接抛出空指针导致 HTTP 500（car.jsp 第 109 行），在高并发、会话失效场景下会放大异常比例。

## 八、优化建议

1. **优化登录链路**：将用户信息校验结果或用户对象缓存（项目已引入 ehcache，可直接启用），减少每次登录的 Hibernate 查询与 Session 创建开销；对 Action 层使用 Spring 单例作用域；对密码校验增加必要的索引与加盐缓存。预期可将登录响应时间降低 50% 以上。
2. **统一并调优数据库连接池**：移除多余的 dbcp/c3p0/proxool 依赖，只保留一种连接池并显式配置最大连接数（建议 50～100）、最小空闲连接与超时回收，避免连接获取成为串行瓶颈。
3. **引入页面与数据缓存**：对首页商品列表、公告列表、轮播图等读多写少的数据启用 ehcache 缓存并设置合理过期时间，可大幅降低数据库压力。
4. **调整 Tomcat 与 JVM 参数**：在 server.xml 中配置 maxThreads（建议 300～500）、acceptCount、启用 gzip 压缩；为 Tomcat 配置 -Xms/-Xmx（建议 1G～2G）与合适的 GC 策略，解决高负载下的进程退出问题。
5. **静态资源优化**：将图片、CSS、JS 交由 Nginx 或浏览器缓存（设置 Cache-Control/ETag），减少应用服务器请求量；本次测试中首页响应体达 39 KB，其中静态资源占比可观。
6. **增强健壮性与异常处理**：对依赖会话的页面统一增加判空并重定向到登录页，避免直接抛出 500；为关键接口增加限流与降级措施，防止突发流量击垮服务。

## 九、测试结论

本次测试围绕农产品溯源电商平台的 7 个核心接口与 1 条完整业务流程，设计了 20、50、100、200 四档并发（各持续 60 秒）及 50 并发持续 120 秒、10 并发业务流程共 6 个场景，累计产生 557,317 个请求样本。

主要指标表现：在 20 并发基础负载下平均响应时间 13.8 ms、P95 103 ms、吞吐量 1386/s；并发升至 200 时平均响应时间 95.7 ms、P95 853 ms、P99 1256.8 ms、吞吐量 2013/s；全部场景错误率均为 0.00%。完整业务流程（登录→浏览→加购→查看购物车→退出）全部通过，平均响应 10.1 ms。

结论如下：

1. 系统在 200 并发以内的短时负载下具备良好可用性，全部请求成功处理，未出现错误；
2. 系统处理能力存在明显天花板：并发提升 10 倍时吞吐量仅提升约 45%，响应时间呈近线性上升，说明已接近饱和区间，需通过缓存与连接池调优提升单位时间处理能力；
3. 性能瓶颈集中在会员登录接口（涉及 MD5 计算、HQL 查询与会话写入，且无缓存），其在 200 并发下的响应时间（654.2 ms）是页面类接口（约 3 ms）的 200 倍以上，应优先优化；
4. 页面浏览类接口性能表现优异且在高并发下保持稳定（2～3 ms），说明 JSP 渲染与简单查询不是瓶颈；
5. 测试中发现 200 并发及长时间持续压力后 Tomcat 进程自行退出的稳定性问题，以及会话缺失时抛出 500 的健壮性问题，需在上线前修复。

综上，系统能够满足中小规模并发访问（约 50～100 并发）的性能要求，但要支撑更大规模访问，需按第八章建议完成缓存、连接池、Tomcat/JVM 参数三方面的优化后再次回归测试。
